Thermal Controller & Logger

Building a Python workflow for multichannel trends and traceable test reports.

ENGINEERING EVIDENCE / AT A GLANCE

Contribution, evidence, and limitations

Problem

Make repetitive temperature tests easier to monitor, compare, and document.

My contribution

Built the Python acquisition, trend-display, and reporting workflow; later documented recovered architecture and added a CSV audit utility.

Engineering tools

Python, Tkinter, Pico TC-08, thermocouples, CSV/Excel, and an optional Arduino serial interface.

Validation method

Inspected the original Python workflow, checked a separate CSV audit utility, and independently reproduced ten synthetic trend-label edge cases. No original hardware test was run.

Documented result

Public source supports eight channels and CSV/Excel reports; trend-label analysis reveals missing-reading and wide-fluctuation edge cases.

Limitations

“Stable” is a software label, not proven thermal equilibrium. Hardware calibration, acquisition timing, and companion Arduino firmware remain unverified.

Engineering decisions

Keep capture and reporting traceable

The application saves test metadata with channel readings and supports CSV plus optional formatted Excel output. Plotting retains a bounded history while logging continues independently, separating the display from the record of the test.

Make the trend rule explicit

The original interface retains up to 10 valid readings per channel and uses a 3.0 °C maximum-minus-minimum threshold, but labels can appear after only two readings. When a wide-fluctuation window starts and ends at the same value, the source still labels it “stable”. This indicator is not a validated equilibrium criterion.

Testing and results

The original source supports CSV/Excel reporting, a bounded trend display and a nominal 1.0-second UI poll schedule, not verified sample timing. A separate CSV audit utility passed four synthetic checks. A new, independent trend-label review reproduces 10 source-based synthetic edge cases, including an out-of-band fluctuation the original interface still calls “stable”. Neither review measures hardware performance.

Next verification step

Record actual acquisition timestamps, validate the TC-08 and driver interface on hardware, and recover and test the optional Arduino control path.

Data capture and reporting

Test metadata, selected temperature channels and sample numbers are exported to CSV, with an optional formatted Excel version.

Important timing limitation

Exported sample indices are not actual acquisition timestamps. Sampling jitter, driver accuracy and long-duration reliability require hardware testing.

What the “stable” display label actually means

Source review confirms a default 10-reading history and 3.0 °C full-range threshold. However, the original code can label a channel after just two valid readings and can report “stable” despite a large range when first and last values match. The display text says ±3.0 °C, but the algorithm compares maximum minus minimum to 3.0 °C.

Evidence & limitations

Public source you can inspect: the application interface, plotting module, and logging logic. The workflow illustrations describe the software architecture, not a live hardware test.

Independent code review: Trend-label semantics and edge-case audit compares the original source behavior with a separate proposed stricter review policy. It identifies no new physical measurements.

Evidence boundary: Public software files are inspectable, but the graphics contain synthetic examples, not measured thermocouple readings. Pico TC-08 calibration and real acquisition timing were not independently revalidated. Internal engineering logs, employer records and proprietary reports are not offered as public downloads.

What a reviewer can verify

  • Inspect application behavior: Available: public Python UI, graphing and logging modules for the temperature workflow.
  • Check the software reconstruction: Available: four synthetic checks of a separate CSV audit utility, plus ten source-aligned trend-label examples and proposed conservative-review comparisons. Neither is physical test data.
  • Validate an instrumented test: Requires: calibrated thermocouples, hardware timestamp checks, recovered optional Arduino firmware and traceable readings.
